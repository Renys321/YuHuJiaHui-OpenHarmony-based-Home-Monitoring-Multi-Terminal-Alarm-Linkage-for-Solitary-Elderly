## 二、esp32-sos 解析失败 —— 定案（Lead 指定优先项）

### 2.1 失败发生在哪个 socket 分支
`bridge/mqtt_bridge.js:809` 的 `logErr('[bridge] 状态行解析失败:', line.slice(0, 80))` 位于 `attachNode()` 的 `s.on('data')` 处理器内（765-826 行），即 **`--status-tcp 127.0.0.1:9001` 板端端点读分支**。

排除另两条分支：
- 不是 `--listen 9101` 无线节点：那里失败文案是 `[bridge] 无线节点报文解析失败:`（909 行），本次 0 条；
- 不是 `--relay-to` 注入通道：那是写方向，不解析。
→ 坏报文是**板上 homemon 经 hdc fport 9001 广播给 bridge 的 status 行**。

### 2.2 上游写入端是谁
**不是 wearable-mirror，也不是 video 的 server.js。** 两处都排除，且各有一条硬证据：

- `cloud/wearable-mirror/src/transport.js:96`：`this.socket.write(`relay ${line}\n`)` —— 前缀、换行、单次写入都正确；
  `runtime/mirror-status.json`（01:52）：relay transport `connects:1, disconnects:0, linesSent:624, lastError:""`，`sourceStatus.polls=1153, ok=1153, errors=0`。**发送端 49 分钟零错误、帧完整。**
- `video` 的 `server.js --transport relay` 用 WebSocket 帧边界，且它那条 9001 连接是取视频帧通道，不写 esp32-sos 状态行。

损坏发生在 mirror **之后**：板端 homemon 把 `relay <json>` 广播回所有客户端时，**同一帧内被插入一段 52–102 字节的重复片段**。

### 2.3 分帧性质（逐条排除）
用只在 9001 上 connect+read 的只读抓包（`_tcp9001_raw.bin` 76.4s、`_tcp9001_raw2.bin` 180s）拿到原始字节：

```
49 个 esp32-sos 帧 / 4 个坏帧 = 8.2%（≈0.93 坏帧/分，与 bridge.err 的 1.16 条/分同量级）
正常 esp32-sos 帧 = 804 B（是全部广播类型里最长的：kitchen 410 / bath 405 / dayu200 527）
坏帧长度           = 906(+102) / 857(+53) / 856(+52)
坏帧括号数         = "{"=11 vs "}"=10（结构不平衡）
删掉插入片段后     = ConvertFrom-Json 成功，deviceId/state/ts 完全正确
```

**排除**：
- 不是**缺换行/分帧错位**——坏帧仍以 `\n` 正确结束，其后一行解析正常，**无级联污染**；
- 不是**前缀未剥离**——坏帧首字节直接是 `{`，无 `relay `/`route ` 残留；
- 不是**UTF-8 截断/编码**——载荷为 ASCII+中文，坏帧处无乱码替换符；
- 不是**多重 JSON 拼接**——不是 `{...}{...}`，是**同一帧内部插入了一段更早出现过的字节**（`窗口[754,806) 与更早位置 702 重复` 的特征），插入量 = 帧长的 6%–13%。

**指向**："长帧 + 共享发送缓冲/分片边界"敏感路径。板端 `southbound/src/homemon.c:717-747` 的 `tcp_send_best_effort` 是"整行 send + 单独发 `\n`"的非阻塞尽力发送，EAGAIN 半包时 `return -1` 后直接 close（只会截断/丢帧，不会产生重复字节），因此损坏点更可能在 **homemon 行组装缓冲** 或 **hdc fport 的共享转发层**；仅靠 PC 侧只读手段无法再二分（需板端代码/抓 USB 侧）。

**跨通道同时性（关键旁证）**：
```
我的抓包坏帧 ts = 1793123044325
bridge.err      = [2026-10-27T17:44:14.135Z] 状态行解析失败: ..."ts":1793123044325 ...
```
两个独立 fport 通道收到**完全相同**的坏帧 → 损坏发生在"一次组装、广播给所有客户端"的上游，而非各通道独立读侧。

### 2.4 影响面：是否"从未进入 bridge/MQTT/云端/APP"
分三路说清，避免把"设计上忽略"和"解析失败"混为一谈：

| 目的地 | 是否受影响 | 说明 |
|---|---|---|
| bridge → MQTT 上行 | **本来就不该进** | `--relay-ignore esp32-sos` 设计：板端回灌的 esp32-sos 一律 `continue`，不发布、不退休板端连接（本次 442 次命中被忽略）。坏帧只是"没走到 ignore 就被 parse 拦下"，**结果等价**：都不发布。 |
| 云端 / 手机 APP | **不受影响** | esp32-sos 走独立链路：4G → ECS `api.luxunacc.xyz` → backend；mirror 以 `--source api` 轮询（1153 次 / 0 错误）。这条路完全不经过 hdc fport 的广播。 |
| 板载 APP 的求助状态显示 | **受轻微影响** | mirror 把 esp32-sos 状态注入 homemon，homemon 广播给板载 APP —— 走的正是这条 8.2% 损坏的广播。坏帧 = 该次更新丢失，下一个心跳（5s）即恢复。 |

### 2.5 明确判断（回答 Lead 第 4 问）
**不会表现为"随身求助按了没反应/APP 看不到"。**
- 求助是否"有反应"取决于两条独立链：① 云端/手机 APP 走 4G→ECS→backend（本次 0 错误）；② 板载显示走 mirror→homemon 广播（本缺陷所在）。②的单帧丢失会被 5s 心跳覆盖，最坏只是**板载 APP 的求助状态最多晚 ≤5 秒显示**。
- 另外本次 bridge 的求助播报编排是关闭的（`求助播报 : 关闭（未提供 --sos-source / --sos-targets）`），不存在"因坏帧导致厨房/卫生间播报不触发"的链路。
- 结论：**这是日志里持续存在、看起来吓人、但演示影响可忽略的 DEGRADED 缺陷**；真正需要盯的是第 14 项 hdc fport 与第 4 项 Wi-Fi 同断。

## 五、结论句与"最先失效环节"排序

### 5.1 当前链路稳不稳
**稳。** 判据：50.9 分钟内 ①PC 侧四条长连接源端口零漂移；②MQTT 零重连/零重放/零协议错误；③事件速率均匀（54–65/min，无分钟级缺口）；④RSS/句柄/线程零增长；⑤探活 100% 通过、环回 1ms；⑥状态转发 2121 条、60s 抽样 42 帧零丢帧、dayu 间隔抖动仅 0.5%。
**不完全稳的地方**：板端广播有 8.2% 长帧字节损坏（不影响主链路）；Wi-Fi 层已发生 1 次双节点同断 12.5s。

### 5.2 演示期间最可能先坏在哪（按概率×影响排序）

1. **hdc fport（PC↔USB↔板端）—— 第一失效点。**
   它是**单点**且承担 dayu200 全部状态与全部 relay 注入；已实测长帧 8.2% 损坏（能力已不是 100% 干净）；`KNOWN-RISKS.md` P1#3 白纸黑字"fport 规则会随连接消失，Bridge 会持续重连但 APP 收不到无线状态"。演示中任何 USB 松动/板端重连/`hdc` 服务重启，都会**同时切断 bridge 的 status-tcp、relay-to 与视频 9001**，表现为"APP 里所有房间一起不动"。
   *可观察前兆*：`hdc fport ls` 变空、bridge 9001 端点重连日志、dayu200-living 状态断流。

2. **ESP32 Wi-Fi 接入（两块板同时掉线）—— 已发生过一次。**
   01:43:48 两板相隔 714ms 同时断开、12.5s 后自愈，说明是**共因（AP/信道/PC 网卡）**而非单板故障；演示前若热点不稳会再来一次，表现为两个房间状态同时停更十几秒。bridge 能自愈（已验证），但演示窗口期内的空档是可见的。

3. **单 broker / 单 bridge 进程（无冗余）。**
   任一进程挂掉即全链路断；本次 50.9 分钟两者零异常、RSS 平，短期概率低，但没有任何自动切换。

4. **板端 homemon 的 8 个客户端槽位。**
   源码注释记录过"4 路占满导致新连接 accept 后立刻关闭"的现场事故；当前占 4/8。演示若叠加多终端观看/多次健康检查/异常断开的僵尸连接，会触发"新连接连上就被踢"。演示前建议只保留必需客户端。

5. **QoS 0 + 无 retain + 无鉴权/无 TLS（既有设计约束）。**
   订阅端瞬断那一条消息必丢，恢复依赖 bridge 的"重连后重放最后状态"（本次 0 触发，逻辑在 `mqtt_bridge.js:754-763`）。对单次演示推送影响有限，但**不能宣称"消息不丢"**。

### 5.3 给演示的三条最低成本建议（只读结论，不含任何改动）
1. 演示前与演示中**每秒盯一眼** `hdc fport ls` 是否仍为 `tcp:9001 tcp:9000 [Forward]`，这是成本最低、覆盖面最大的预警（第 1 失效点）。
2. 别在演示前做"端口探活/多终端订阅"之类的动作：它们会占板端客户端槽位（第 4 风险）并制造误报式日志。
3. 若演示必须依赖板载 APP 显示随身求助，把"按下后状态可能出现 ≤5s 延迟"当作已知表现，不要在按下 1–2 秒内就判定失败（第 1 项缺陷）。
