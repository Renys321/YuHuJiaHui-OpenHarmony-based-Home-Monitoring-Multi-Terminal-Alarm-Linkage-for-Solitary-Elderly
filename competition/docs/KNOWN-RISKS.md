# 已知风险与处理顺序

更新时间：2026-11-01（Asia/Shanghai）

## P0：扩展前必须守住的版本边界

### 公网后端已上线，但手机到实体设备尚未形成真实链路

公网 HTTPS 后端已经在 ECS 上线，DNS、公共证书、Caddy、容器健康、真实 APP 登录和 API 合同通过。仍未完成的是家庭网关上传真实 DAYU/ESP32 状态、队友 APP 手机真机、APP ACK 下发实体设备及 `ACKED` 回传。公网后端 PASS 不能外推为“手机 APP 已完成”或“手机到设备闭环已完成”。

处理：启动本地 Broker、Bridge 和实体设备后运行 `cloud/onenet/public-sync.js`；用户只在终端隐藏提示中输入服务器 `INGEST_KEY`，不得进入源码、聊天、命令行、环境变量或日志。先验收真实状态上传，再由队友 APP 创建 ACK 并保存脱敏实体回执证据。OneNET 常驻验收是独立扩展，不再阻塞 HTTPS APP 主链路。

### 0.2 网关第一阶段的下行能力有意收窄

`cloud/onenet/gateway.js` 只执行“网关自身 `RESET`”，且必须等真实设备回执才回复 `code=200`。
物模型 `control` 目前没有 `deviceId`，因此 `ACK` 与 `SET_CONFIG` 一律回失败——这是刻意的安全选择，
不是缺陷：在没有明确设备绑定的情况下按“当前房间”猜测会误伤其他房间。

处理：若要打通家属手机确认闭环，先给 `control` 增加可选 `deviceId` 并同步修改
`cloud/onenet/thing-model*.json`、`adapter.js` 白名单与其 17 项测试，再扩展网关下行。

### 4G/GNSS 与语音电话能力不能混用

YED-M100MG-B1 资料支持数据、GNSS 和可选短信，但没有语音音频接口证据。GNSS 还是选配且室内可能无效。当前不能宣称它能自动拨打语音电话。

处理：用脱敏串口脚本确认固件、CSQ、注册和 GNSS 子型号；手机一键拨号走 `wx.makePhoneCall`。若需求是设备无人值守自动外呼，另选明确支持 VoLTE/音频的模块或第三方呼叫服务。

### 0. 自动监护通道已通过，真人准确率与后台常驻未通过

APP 前台时 Surface 就绪会自动启动 Camera 和 USB 有界送帧；显式暂停、恢复、Ability 前后台
释放/恢复，以及合成 FALL 到 APP 待处理再由 APP ACKED 的真机闭环已经通过。该结果只证明
前台运行和告警通道。当前本地自动取证已经通过：PC 保存真正触发判定的帧，DAYU 同一
evidenceId 只自动拍一张高分辨率照片。可信后端上传、精确告警绑定、30 天/200 条保留和微信
授权下载/预览代码已完成本地测试，公网 API 已部署，但还没有真实家庭图片上传、正式微信 AppID 或手机真机预览证据。系统重启
自启动、应用被杀后常驻、后台相机策略、真人跌倒/坐下/弯腰/躺床/遮挡数据集仍未完成，当前阈值只是演示基线。

处理：固定机位、标注床/沙发排除区并采集分场景视频；家庭授权、HTTPS 客户端约束和后端
过期删除已补本地实现，仍需公网/微信真机验收。DAYU 私有照片已经实现严格文件名过滤、保护当前照片和最多 100 张的数量清理，并通过 API 26 构建；新 HAP 尚未签名安装，也未做 101 张真机边界测试。后台相机必须单独设计并验证 OpenHarmony 策略，不能由前台 PASS 外推。短时真机
只有约 2 FPS，持续 FPS、CPU、内存、温升和长时重连仍需验收。
PC 图片上传已改为同证据目录的原子持久 outbox，断网和进程重启会恢复 pending，并以 uploaded
回执避免正常重启重复发送；本地损坏图片不会上传，状态文件不保存密钥。它仍受本地证据 200 条、
单进程单目录和磁盘可用性约束，不得宣传为无限期或零丢失存储。
`score` 只能称为证据分，不是概率；未统计召回率和误报率前不得作医学准确率宣传。

PC 视觉服务已经能在无新帧时定时重试待发 FALL，并在 30 秒后丢弃陈旧事件。2026-10-14 起 PC
watchdog 把「长期收不到 DAYU 帧」变成可路由事件：`{"cmd":"monitor"}` → Bridge → homemon 的
`monitorOnline` 字段 → 状态广播 → APP 显示「PC 监护失联」，恢复来帧后回到「PC 监护在线」
（代码与协议见 `docs/evidence/2026-10-14-monitor-offline-watchdog.md`）。**该通知止于板载 APP**：
到家属手机/公网小程序仍未完成，检测延迟等于 `--frame-timeout-ms`（默认 10 s），且 PC 服务
从未启动过时 `monitorOnline` 停在 `-1`（APP 不误报失联）。不得把「无人值守监护失效也会远端
告知」写成已完成能力。

后台相机 / 开机自启 / 被杀恢复没有合法实现路径：API 26 的 `BackgroundMode` 没有任何相机类型，
`TASK_KEEPING` 与 `MODE_SPECIAL_SCENARIO_PROCESSING` 需要受限 ACL 权限
（`KEEP_BACKGROUND_RUNNING_SYSTEM` / `..._SPECIAL_SCENARIO`），`MODE_AV_PLAYBACK_AND_RECORD`
属媒体录制场景；本仓也未申请 `KEEP_BACKGROUND_RUNNING` 或 `backgroundModes`。这三项保持
NOT IMPLEMENTED，不得用定时器、前台服务或媒体后台类型伪装成已实现。

当前视觉测试 56/56、Bridge 集成测试 18/18、旧 HAP 构建/签名/验签/安装、真实 DAYU 本地自动
取证和 APP 失联/恢复显示均已通过。剩余风险是通知和照片仍止于本地，后台相机、开机自启、
长时稳定性和公网手机端尚未完成。PC HTTP 服务已捕获客户端提前断开，并用三种断连异常在
响应头/响应体阶段做了自动化回归；长时稳定性仍需另测。

## P1：工具、制品与运行环境

### 3. HDC fport 会随连接消失

保活 PowerShell 进程仍存在不代表 fport 规则仍有效。板端断开后 `hdc fport ls` 可能为空，Bridge 会持续重连但 APP 收不到无线状态。

处理：一键启动脚本已支持 `-BridgePort 9101 -FportPort 9001`；每次启动仍必须核对 `hdc list targets`、`hdc fport ls` 和 Bridge 的转发目标连接日志。

### 4. DAYU 重启后系统时间回退（已实测确认）

设备没有 RTC 电池，重启后可能丢失系统时间。Unix epoch 使用 UTC，不得人为增加 `28800` 秒；历史 8 小时问题是本地显示与 UTC 混淆。

**2026-10-14 再次确认该风险成立**：虽然 2026-10-13 曾校准成功，本轮板端 `date -u` 又回退
到 2017 年；自动抓拍 JPEG 有效，但以板端 epoch 生成的照片文件名时间不可信。旧证据还记录过
2021 年回退。后果：板端自身生成的 `ts` 即使是 13 位毫秒，数值也可能错误，不能直接作为
云端时间或告警时间依据。当前复现见 `docs/evidence/2026-10-14-fall-auto-evidence.md`。

处理：将网络校时或从可信主机校时纳入启动流程，并同时用 `date -u` 和 PC epoch 验证。云端上云时间使用 PC 本地接收时间（网关已如此实现），但这只是绕过，不代表板端时间已修好。取证时继续同时记录 PC 与设备时间。

### 5. ESP32 当前是演示阈值

`CONFIG_NODE_NO_MOTION_SEC=30`，且 PIR 未接时会持续产生 `NO_MOTION` 告警。这是当前配置的预期行为，不是固件故障。

处理：演示时接入 PIR，或正式运行前恢复到 1800 秒。

**DAYU200 历史 GPIO 问题（2026-10-10 实测，2026-10-13 已修）**：旧演示配置把 GPIO 29 当 PIR，
但正式映射中 29 是门磁；悬空/持续高电平还会让旧代码每秒累计一次活动。当前 `homemon.c`
已改为每路激活沿只计一次，`demo_start.ps1` 默认不读取实体 GPIO 且阈值为 1800 秒；只有接线后
显式传入 `-UsePhysicalSensors` 才启用 PIR 117/114 和门磁 29。默认配置真机 10 秒计数增量为 0。
实体 PIR/门磁尚未接线验收，因此不能把本次“无假计数”外推为传感器效果 PASS。

### 6. HDC 默认临时目录在本机可能不可写

默认 HDC server 曾无法创建 `%TEMP%\.hdc.cache.log`，错误为 `operation not permitted`。第三轮通过为本轮证据目录设置独立 `TEMP/TMP` 解决。

处理：若复现，按 `RUNBOOK.md` 创建独立 HDC 运行目录。不要泛杀 HDC server，也不要复用或删除历史证据目录。

### 7. 签名 profile 的设备标识需重新核对

签名 profile 使用的 provision UDID 与 HDC target ID 是不同字段；旧辅助脚本还指向另一个工程。

处理：重新生成 profile 前从当前设备查询 provision UDID，只把 `eldercare-signed.hap` 作为当前已验证 signed HAP。

## 2026-10-31 ESP32-S3 板载咪头接入（厨房/卫生间）

### ES8388 ADC 必须同时打开 MICBIAS 与 ADC DLL/参考电压

- 现象：ADC 配置完成后 I2S 读到全 0（`rms=0`，94400 样本），PC 音箱与 1 kHz 音调均无反应。
- 根因：`0x03=0x09` 会保持 MICBIAS 掉电；播放配置收尾 `0x02=0x0A` 会关掉 ADC DLL（bit3）
  与 ADC 参考电压（bit1）。只改输入选择或增益不会恢复。
- 处理：采集前 `0x03=0xFF` → 延迟 → `0x02=0x00`、`0x0A=0x00`（LINPUT1/RINPUT1 板载 MIC1），
  最后 `0x03=0x00`；采集结束 uninstall RX 后重跑 `codec_start` 恢复 DAC/功放，
  日志有 `MIC end playback_restored=1`。
- 证据：厨房近场蜂鸣 5 s `rms 76→229`，卫生间 5 s `rms 11→881`；两块板播放恢复正常。

### 立体声交织必须下混为单声道

ES8388 ADC 以立体声交织输出。只取一路会让网关收到 32 kHz 样本流，时长与语速翻倍。
`local_voice_mic_read()` 现按 `(L+R)/2` 下混，3 s 采集得到 47360 样本（≈2.96 s @16 kHz）。

### 9302 广播的边界（2026-11-01）

- 广播只覆盖已完成 `hello` 握手的 9302 连接；板端重插/重启或网关重启后，
  必须重新 `hdc rport tcp:9302 tcp:9302`，否则板端显示“语音网关未连接”。
- `speakers` 是当时 TCP 连接数，可能含未清理的旧连接；只作参考，不代表可播节点数。
- 广播事件不含 `alarmId`，因此 S3 实采事件在手机 APP 中点击只会提示
  “该记录无关联预警”，不会跳转；只有带 `alarmId` 的记录才跳转原告警详情。
- 慢客户端（写缓冲 > 256 KiB）会被移出广播集合，需重连后才能继续接收。

### 本地 clip 经 9102 永远静音（解析 bug，2026-11-01 已修复并刷两板）

- 现象：DAYU 快捷提问命中健康问题时，网关日志显示 `本地片段播报：clip=9 推送到 1 个节点`，
  但喇叭没有声音；同一时刻网络 PCM 回答正常。
- 根因：`speaker_link.c` 用 `parse_int_field(line, "\"clip\"", 0)` 解析
  `{"type":"clip","clip":9}`，`strstr` 先命中的是 type 的取值 `"clip"`，其后紧接 `,`
  而不是数字，函数返回 fallback 0 → `local_voice_play(0)` 等于取消，整段静音。
  该路径没有节点回执，网关侧无法发现。
- 修复：改为按 `"clip":` 键取值（`atoi(clipKey + 7)`），日志加 `(key-parse)` 便于核验；
  `common` 修改后 `firmware/tools/sync-shared.ps1` 同步 kitchen/bathroom，两工程重建并逐板刷写。
- 证据：`logs/com6-clip-fix.log`：`RX local clip=9 (key-parse)` → `PLAY clip=9 bytes=93488`
  → 11.75s 后 `STOP clip=9 result=ESP_OK cancelled=0`。
- 边界：该 bug 只影响 9102 推 clip 的路径；KEY1 健康语音走 9303 另一套解析，一直正常。
