# 交给 Codex 的提示词：设计方案 DOCX + 答辩 PPT

> 用法：在 Codex 中打开仓库 `<WORKSPACE>\competition`（或整个 `<WORKSPACE>`），
> 先发「提示词 0」让它读材料并给出事实清单/大纲；你确认大纲后，再分别发「提示词 1（DOCX）」
> 和「提示词 2（PPT）」。最后用「提示词 3」做盲审与事实核查。
>
> 关键约束来自官方《作品提交要求》：
> - 提交材料：设计方案 Word（.docx）、演示视频（mp4 ≤100MB/≤5 分钟）、答辩 PPT（汇报 ≤7 分钟）、完整源码包；
> - 全部材料**严禁出现学校名称、队员、指导教师等身份信息**（盲审）；
> - AI 仅可作辅助工具（≤30% 工作量），核心内容必须人工修改、调试、验证；答辩要能解释核心业务逻辑与技术实现；
> - 提交窗口 2026-11-04～11-06，提交后原则上不可替换。

## 提示词 1：生成《设计方案》DOCX

```
基于你刚才确认的大纲与事实清单，生成「设计方案」Word 文档，保存为：
<WORKSPACE>\competition\docs\submission\设计方案.docx
（若目录不存在先创建；用 python-docx 生成，不要手工拼 XML。）

作品信息：
- 作品名：域护家徽：OpenHarmony 驱动的独居老人居家安全监测与多端告警闭环系统
- 赛题：赛题四 · 独居老人居家安全监测与应急辅助系统
- 定位一句话：面向独居老人的"端—边—云—应用"居家安全系统，本地优先报警、设备级 ACK 闭环、可扩展多节点。

文档结构（可按内容微调，但必须覆盖）：
1. 作品概述（赛题理解、目标用户、核心价值、与常见方案差异）
2. 需求分析（功能需求、非功能需求：可靠/隐私/适老/成本；优先级）
3. 总体架构（分层图：设备/边缘/传输/云/应用；端口与进程表；6 条数据流：状态上行、命令下行、ACK 闭环、视频、视觉跌倒、随身 SOS）
4. 硬件设计（DAYU200 边缘主控、ESP32-S3 节点、传感器与接线、供电与共因、随身 4G 设备；给出引脚/接口表）
5. 软件设计
   5.1 设备端固件（ESP-IDF/FreeRTOS、ADC/I2C/I2S、JSON 行协议、三节点配置化）
   5.2 边缘 homemon（C：采集/判定/声光/语音/状态机/ACK/route/relay）
   5.3 传输层（bridge 行协议↔MQTT、自包含 broker、public-sync、命令队列、幂等与重试）
   5.4 云端后端（Node 原生 http、鉴权、状态/告警/命令/证据/通知、JSON 文件原子存储）
   5.5 应用端（手机 APP 分层、板载 APP、能力模型、在线判定、ACK 交互）
   5.6 视觉与视频（YOLO11n-pose + 时序规则状态机、受限 fall 事件、JPEG over WS）
6. 关键设计与创新（本地优先闭环、设备级 ACK、受限视觉事件、多节点协议同构、可解释判定、可靠性设计；每条给"做法/对比/证据/边界"）
7. 安全与隐私（密钥不落盘、鉴权、证据留存策略；明确边界：局域网设备链路无 TLS/鉴权、ECS 单点）
8. 测试与验证（能力矩阵表：已实测/PARTIAL/未实测/未实现；引用 VALIDATION-MATRIX 与 evidence 目录；写明测试方法与限制，禁止编造）
9. 部署与运维（一键入口、端口/进程、故障自愈、回滚）
10. 推广与成本（BOM/部署成本、可复制性、商业模式设想；若没有数据就写"估算口径"）
11. 边界与后续计划（KNOWN-RISKS、07-IMPROVEMENTS 的 P0/P1）
12. 附录（协议字段、API 摘要、术语表；AI 辅助工具使用说明——仅写"用于文档润色/代码提示/UI 素材等辅助环节，核心代码与验证由团队完成"，不得出现身份信息）

格式要求：
- A4；正文宋体小四、1.5 倍行距；标题黑体；自动目录；页码；图表编号与题注；表格统一三线表风格。
- 架构图/数据流图/时序图：至少 4 张（总体架构、状态上行、命令+ACK、视觉跌倒链路），可用 matplotlib/graphviz 生成 PNG 插入，风格简洁、中文标注。
- 页数 18–28 页，正文 7000–10000 字；不要空话，每节要有具体机制/参数/文件依据。
- 禁止出现：学校/学院/教师/队员/队名、内部代号、绝对路径、密钥、未验证的量化指标（如"准确率 95%"）。
- 设置 docx 核心属性为中立值（作者/最后修改者留空或"参赛作品"）。
- 生成后自检：目录页码正确、图表可打开、无占位符、无身份信息、与事实清单一致。

最后输出：文件路径、页数、图表数、字数、你标注为"未实测"的内容清单。
```

## 提示词 2：生成《答辩 PPT》

```
基于已确认的大纲与事实清单，生成答辩 PPT，保存为：
<WORKSPACE>\competition\docs\submission\答辩PPT.pptx
（用 python-pptx 生成，16:9，可编辑文本框，不要整页贴图片。）

约束：
- 汇报时长 ≤ 7 分钟（建议 12–14 页，每页讲 25–35 秒）；
- 全部材料盲审：不出现学校/学院/指导教师/队员/队名/校徽/门牌；封面只写作品名 + 赛题四；
- 每页一个结论句（标题即结论），正文 ≤5 条、每条 ≤18 字；字号 ≥20pt；
- 演讲者备注写 30–50 秒口播稿（含演示动作提示）；
- 不虚构指标；需要数字时只用材料中可核实的（如端口号、节点数、实测帧率区间、证据目录）。

建议页序：
1. 封面：作品名 + 赛题四 + 一句话价值（不放校名/队名）
2. 痛点与目标用户（独居老人/子女/社区；现有方案断网即哑、假闭环、加节点难）
3. 方案总览（一张分层架构图：设备→边缘→PC 网关→云→手机 APP）
4. 硬件与边缘（DAYU200 + ESP32 节点 + 传感器；本地声光语音）
5. 核心链路 1：状态上行 + 多终端同步（设备→bridge→MQTT→云→多手机）
6. 核心链路 2：设备级 ACK 闭环（HTTP 202≠闭环，alarmId 精确匹配）
7. 核心链路 3：视觉跌倒（YOLO pose + 时序状态机 → 受限 fall 事件 → homemon 统一告警；给 NORMAL→SUSPECTED→FALLEN 的实测截图/日志）
8. 可扩展多节点（ESP32 不实现 MQTT，JSON 行协议同构，新增房间零改代码；三节点配置表）
9. 视频探望与随身 SOS（票据+WS；4G 旁路镜像）
10. 可靠性工程（supervisor/熔断/心跳、幂等、fport 自愈、IP 漂移解析）
11. 验证与演示（能力矩阵摘录：已实测/未实测；给出实拍/UI 证据；明确"演示机位调参"边界）
12. 创新点总结（4 条，对应赛题创新拓展：多终端同步/可扩展多节点/本地优先闭环 + 设备级 ACK）
13. 边界与后续（单点、安全、视觉准确率；P0/P1 改进）
14. 结束页（作品名 + 一句话；不放身份信息）

图表：架构图、ACK 时序图、跌倒状态机/实测轨迹图、节点扩展示意；从 evidence 中挑真实截图（UI dump 渲染或现有 jpeg/png），不要用 AI 生成"假界面"。
生成后自检：页数、每页字数、有无身份信息、备注是否超时（按 7 分钟总时长估算）；输出 PPT 文件路径、页数、预计讲解时长、需人工替换的截图清单。
```

## 提示词 3：盲审与事实核查（生成后跑一遍）

```
检查 <WORKSPACE>\competition\docs\submission\设计方案.docx 和 答辩PPT.pptx：
1) 盲审：搜索并列出所有可能泄露身份的信息（学校/学院/教师/队员/队名/校徽/文档属性作者/PPT 备注/图片元数据）；
2) 事实：逐条核对数字与结论是否与 docs/VALIDATION-MATRIX.md、evidence/ 下的证据一致；把"未实测"写成"已验证"的地方列出来；
3) 合规：是否有夸大（准确率/用户量/获奖/安全认证）、是否有绝对路径/密钥/内部代号；
4) 结构：PPT 页数与 7 分钟是否匹配（按每页 30 秒估算）、DOCX 目录/图表/页码是否正常。
输出一份"必须修改项"清单（按严重度排序），不要自动改文件。
```

## 给 Codex 的补充事实（可直接贴进对话）

- 系统组成：ESP32-S3 房间节点（厨房/卫生间在板运行，客厅为候选未部署）、DAYU200 边缘主控（homemon + 板载 APP + 摄像头）、Windows PC（bridge/broker/public-sync/视觉/视频/随身 mirror）、ECS（Caddy TLS + Node 后端，JSON 文件存储）、手机监护人 APP。
- 关键端口：PC broker 1883、bridge 9101、板端 homemon 9000（hdc fport→PC 9001）、视觉 9200、视频 relay 9443、板端视频 9301。
- 三条硬语义：设备不实现 MQTT（JSON 行同构）；视觉只提交受限 fall 事件；ACK 必须设备回执且 alarmId 精确匹配。
- 三条不要写：AI 跌倒"已验收/准确率"、云端"高可用/安全认证"、多节点"已全部部署"。
- 真实证据目录：`evidence/2026-10-28-fullchain-health/`、`evidence/2026-10-28-fall-live-test/`、`docs/VALIDATION-MATRIX.md`。
