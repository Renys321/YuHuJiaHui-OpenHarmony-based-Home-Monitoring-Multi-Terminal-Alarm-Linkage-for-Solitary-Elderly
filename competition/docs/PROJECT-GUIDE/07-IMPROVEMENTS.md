# 07 · 完善路线（按 ROI 排序）

> 依据：全链路体检（`evidence/2026-10-28-fullchain-health/`）、`docs/KNOWN-RISKS.md`、各层代码与实测。
> 每条都写清：**现状 → 目标 → 怎么改 → 风险 → 怎么验证**。
> 排序原则：先修"演示会翻车/安全会出事"的，再修"能明显提升体验"的，最后做"锦上添花"的。

## P0 · 演示可靠性（不做可能当场翻车）

### P0-1 hdc fport 单点 → 改用板端网络通道
- **现状**：板端 `9000` 只能经 `hdc fport 9001→9000` 到 PC；USB 松动/板端重启/hdc 服务重启都会让
  **APP 全屋停更**（bridge 两路 + mirror + 视频通道一起断）。今晚实测过 13 分钟断链。
- **目标**：状态/命令/relay 主通道走板端 Wi-Fi（板端已有 `wlan0`，视频 9301 已在用），USB 仅作备用。
- **怎么改**：bridge 的 `--status-tcp/--relay-to` 改指 `10.127.130.132:9000`；mirror 的 `--relay-to` 同理；
  `start-demo-supervisor.ps1` 已支持 `-AutoDayuEndpoint`（USB 优先、否则 LAN），把"优先 LAN"做成默认并补充健康探测。
- **风险**：板端 IP 漂移（需 DHCP 保留/静态 IP）、Wi-Fi 抖动（需 keepalive+重连，已有）。
- **验证**：拔掉 USB 后 APP 仍 4/4 且告警可 ACK；`start-mirror-dayu.ps1 -PreferLan`。

### P0-2 两路 ESP32 共因断线 → 供电/信道治理
- **现状**：01:43:48 两块板相隔 714ms 同时断开并重启（`countToday` 清零），指向共用供电或 AP 抖动。
- **目标**：单次断线不影响演示叙事；至少能提前发现。
- **怎么改**：两块板**独立供电**（不要共 USB HUB/插排）；AP 固定信道（当前 Channel 1）、关自动换信道；
  给 PC 网卡与 ESP32 做 DHCP 保留；bridge 增加"同一秒双节点断开"告警日志/声音提示。
- **验证**：连续 2 小时不出现成对断开；`bridge.out.log` 无成对 `无线节点断开`。

### P0-3 public-sync 换代需人工 INGEST_KEY → 托管密钥
- **现状**：supervisor 启动必须有人在可见窗口输入 key；今晚已因此断流 6 分钟。进程死→云端停更，
  但 `state.json` 可能仍写 HEALTHY。
- **怎么改**：把 key 放进 Windows 凭据管理器/环境注入（supervisor 已支持从 TTY 读，可加 `--key-env`/`--key-file` 的**受限**选项）；
  或把 INGEST_KEY 换成 ECS 签发的短期 ingest token（自动续期）。
- **风险**：密钥落盘=安全面扩大，需权限收敛（仅服务账户可读）。
- **验证**：杀掉 supervisor 后由 watcher 自动拉起并恢复 202，无需人工介入。

### P0-4 关键进程无服务化
- **现状**：broker/bridge/mirror/video/visual 都是普通进程，靠 watcher 与窗口存活；误关窗口即停。
- **怎么改**：Windows 用"计划任务+开机启动"或 NSSM 注册服务；Linux/ECS 用 systemd（`Restart=always`）。
- **验证**：重启机器后无需人工，`watcher-state.p0=healthy`。

## P1 · 安全与正确性（对外演示/答辩会被问）

### P1-1 局域网链路无身份鉴别/无 TLS
- **现状**：ESP32→bridge 是明文 TCP 行协议；MQTT 无鉴权、QoS 0；`ARCHITECTURE.md` 已明确"仅受控环境"。
- **目标**：至少做到"设备身份 + 防伪造"。
- **怎么改**：①每设备预置 `deviceId + PSK`，上线时做 challenge-response（不传明文密钥）；
  ②bridge 校验 MAC/PSK 后才绑定 deviceId；③MQTT 加用户名口令或 mTLS；④对 `route/relay` 增加签名/来源校验。
- **验证**：伪造 deviceId 无法发布；重放旧状态被拒。

### P1-2 消息不丢的承诺缺失（QoS0 + 无 retain）
- **现状**：订阅端瞬断会丢一条；bridge 靠"重连后重放最后状态"兜底（逻辑已有）。
- **怎么改**：状态改"快照+版本号"（已有覆盖式），事件（告警/门磁）加应用层 ACK+重传队列；
  或换 EMQX + QoS1 + retain（成本变大）。
- **验证**：断开订阅端 30s 再连，能补到最新快照；告警不丢不重（幂等键已具备）。

### P1-3 传感器未标定
- **现状**：MQ-5/MQ-2 只报 raw；阈值 900/700 是工程值；未用真实气体验证。
- **怎么改**：建档标定流程（洁净空气基线 24–48h 预热 → 记录分布 → 定阈值 → 打火机放气验证），
  把基线/阈值写进 `firmware/*/sdkconfig.defaults` 注释与 `docs/VALIDATION-MATRIX.md`。
- **验证**：真实气体能让 raw 越阈值并触发 GAS 告警 + APP 卡片 + ACK 清除。

### P1-4 时间一致性与时钟回退
- **现状**：板端时钟曾回退 5.8 年；现用 `dayu-time-sync.js` 校时，网关用接收时间上云。
- **怎么改**：开机强制校时 + 漂移监控；payload 同时保留 `deviceTs` 与 `serverTs` 并在后端标注来源。
- **验证**：断网 10 分钟再恢复，时间不跳变、告警时间线单调。

### P1-5 视觉跌倒未验收
- **现状**：板端事件在跑，但真人跌倒/误报率未评估；`fall` 事件无"证据帧回溯"闭环。
- **怎么改**：录 20–30 组正负样本（跌倒/坐下/弯腰/宠物），统计召回/误报；加"事件前后 2s 关键帧"证据。
- **验证**：给出混淆矩阵与阈值依据；告警详情能看到证据图。

## P2 · 体验与性能

| 项 | 现状 | 改法 | 收益 |
|---|---|---|---|
| 视频带宽 | JPEG over WS，320×240，无自适应 | 换 H.264/WebRTC；按 RTT/丢包调帧率与质量 | 带宽↓、延迟↓ |
| 推理性能 | PC/板端 CPU 推理，丢帧 29% | RKNN/NPU 适配（`vision/dayu-local` 已备导出链） | 帧率↑、功耗↓ |
| APP 会话 | 仅内存，重启要重登 | 勾选"记住登录"或后端 refresh token | 演示不易掉线 |
| APP 刷新 | 定时轮询 | 改成 SSE/WS 推送或按需刷新 | 实时性↑、请求↓ |
| 告警噪音 | 51 条未确认告警堆着 | 分级/合并/自动归档（同类 5 分钟合并） | 老人/家属不被打爆 |
| 多终端推送 | 后端有骨架，未验收 | 打通短信/微信/APNs 至少一条并验收 | 创新项落地 |

## P3 · 工程化与长期演进

1. **CI**：一条流水线跑「ESP32 三节点编译 + homemon 主机单测 + Node 单测 + APP tsc/测试 + 固件/HAP 哈希」，
   产出 `BUILD-VERIFY` 类证据。现有测试很多，但靠人手跑。
2. **可观测性**：统一 `/healthz`（各进程）、指标（连接数/延迟/失败率/队列深度）、日志轮转与结构化（JSON）。
   现在靠日志文本 + watcher 状态文件。
3. **配置中心**：`sdkconfig.defaults`（设备）、`.env`/compose（云）、APP 能力表（前端）三处配置容易漂移，
   建议生成"设备能力矩阵"单一真源，代码生成前端/后端校验。
4. **固件 OTA**：目前只能 USB 烧录；板端若走 Wi-Fi 通道后可做差分 OTA + 回滚。
5. **数据与隐私**：告警图片/视频的留存期、访问控制、脱敏；APP 隐私政策与授权粒度。
6. **成本**：ECS 单机承载 443/1883；视频若上公网需评估带宽费，优先本地/内网。
7. **代码结构**：`competition/` 下历史目录很多（`esp32-node` 旧构建、`experiments/`、`evidence/`），
   建议把"当前真源"收敛到 `firmware/`、`bridge/`、`cloud/`、`APP/`、`northbound/`、`vision/`、`video/`，
   其余标 `legacy/` 或移出仓库。

## 不建议现在做（会拖累演示）

- 换云平台（OneNET→EMQX/华为云 IoTDA）：适配层已隔离，但不是当前瓶颈；
- 重写前端框架/引入状态管理库：现有 ArkUI + Service 够用；
- 三块 ESP32 同时上线：客厅板未接线验电，先把两块跑稳；
- 引入 K8s/微服务拆分：单机 Node 足够，收益低、风险高。
