## 二、答辩问答（重写）

### 部署场景类

**1. 适合部署在哪些场景？不同场景怎么适配？**

核心场景是城镇社区独居老人家庭，也能复用到农村留守老人住所、养老驿站、敬老院单间。系统是"端—边—云—应用"分层：房间节点走 WiFi 接入家庭网关，随身求助设备走 4G 直连公网，所以不依赖家庭宽带也能保住随身 SOS 这条线；边缘主控（DAYU200）负责本地判定和声光语音，断网也能报警。当前用开发板验证，产品化后再做外壳与防护，部署形态上不挑装修。

**2. 厨房、卫生间潮湿环境稳定性怎么样？**

当前是开发板 + 传感器的验证形态，还没有做工业级防护选型，这点要如实说。但软件上已经做了三件事：设备离线可检测（状态超时判离线）、PIR/门磁/燃气/烟雾按房间独立配置、板端 homemon 本地判定并保留安全日志。正式产品化时再加 IP 防护外壳与防潮选型，这是明确的下一步。

**3. 已装修的房子布线麻烦吗？**

节点是无线接入（WiFi），只有供电线；随身设备走 4G 不需要布线。当前验证形态是 USB 5 V 供电，产品化时会做电池/低功耗版本。整套系统按"房间 + deviceId"配置，迁移时改配置即可复用，不依赖固定布线。

### 实用性

**1. 和市面上的养老监测产品比，真正解决了什么痛点？**

我们的差异化不在"多一个传感器"，而在**把告警闭环做成了硬约束**：很多产品告警弹出来就结束了，我们的链路是"传感器/视觉 → 板端 homemon 判定 → 声光语音本地报警 → 云端/APP → 监护人确认 → **设备必须回 ACK 且 alarmId 精确匹配**才算处置完成"。同时保留本地优先：断网时本地报警照常，不依赖云。这套闭环是真机跑通过的，不是 PPT 概念。

**2. 长时间无活动告警的误报怎么处理？**

不是单阈值拍脑袋。板端支持 PIR、门磁、温湿度、燃气、烟雾多路输入，按房间配置；无活动只是疑似事件，可结合门磁（是否外出）与本地声光提醒给老人取消窗口；视觉跌倒也走"疑似→确认"的时序状态机。当前客厅只启用了 PIR，门磁按房间配置——能力在，配置按现场来。误报数据会沉淀到告警记录里，后续可做规则调优。

**3. 老人不会用智能手机，门槛高不高？**

老人侧零学习成本：环境监测全自动，紧急时按随身 SOS；本地声光与语音播报自动触发。所有查看、确认、处置都在监护人鸿蒙 APP 和板载屏上完成，把操作负担交给子女，这是适老化设计里最实际的一条。

**4. 隐私怎么保障？**

先把话说准：我们**有摄像头**，用于跌倒视觉与按需视频探望，但**不录像、不留存、不把视频存到云端**；视频探望是"票据 + 按需会话"，无人观看 3 秒即断，relay 只转发不落盘。跌倒检测输出的是关键点/事件，不是人脸身份。老人也可以暂停监护（物理遮挡/APP 暂停）。相比 24 小时云存储摄像头方案，隐私暴露面小得多。

### 经济性

**1. 硬件成本和商业推广优势？**

硬件是公开模块（ESP32-S3 节点、DAYU200 边缘主控、常用传感器），成本可估算、可按需裁剪（燃气/烟雾/4G 作为选配）。软件基于 OpenHarmony 自建，**没有平台年费、没有订阅费**，和按月收费的养老 SaaS 是两种模式，适合社区民生项目批量落地。具体 BOM 数字以采购清单为准，答辩不报虚数。

**2. 后期维护压力大吗？**

架构上是模块化的：单点故障只换对应节点；板端 homemon、PC 网关、云端都有健康检查与自愈（supervisor 守护、心跳、fport 自动重建、端点自动解析），现场不需要频繁上门。电量/低电提醒在 APP 侧有预留（当前验证形态供电稳定，产品化再做电池方案）。

**3. 社区大规模采购还能降本吗？**

可以，两条：一是模块化按需裁剪，不买不需要的扩展；二是软件自主、无授权费，社区二次定制不需要额外授权。硬件随批量集采还有空间——这是商业逻辑，不承诺具体折扣。

### 前沿性/科技性

**1. 为什么选 OpenHarmony？**

因为我们要的是"边缘主控 + 多端应用"的国产化闭环：DAYU200（RK3568）跑 OpenHarmony 7.0，板端 homemon 用 C 直接管 GPIO/ADC/I2C 与本地告警，板载 APP 和手机 APP 都用 ArkTS/ArkUI。这样从边缘到应用是同一套国产技术栈，分布式能力、权限模型、多端一致性都是现成的，不用自己造轮子。

**2. 相比 WiFi/蓝牙方案，技术亮点在哪？**

我们不吹"星闪"，亮点是三个真做出来的东西：①**协议同构**——ESP32 节点不实现 MQTT，只发与板端逐字段同构的 JSON 行，桥接按 deviceId 自动路由，**新增房间不用改桥接和 APP**；②**受限视觉事件**——视觉只提交"跌倒"事件，alarmId、声光、ACK 全部由板端统一管，误报不污染告警体系；③**本地优先闭环 + 设备级 ACK**——断网也能报警，处置必须设备回执。这三点比"换个无线协议"更能体现工程能力。

**3. AI 健康评估怎么实现的？**

分两层：安全层是 YOLO11n-pose 关键点 + 时序规则（直立→快速下坠→低位水平）做跌倒事件，可解释、可调参、本地推理；生活层是可选接入大模型（DeepSeek API），把活动时序总结成"生活规律提示"，**只做生活状态参考，不做医疗诊断**。大模型未配置时接口返回 503，APP 不会伪造建议——这也是我们对"AI 不越界"的工程约束。

**4. 断外网还能工作吗？**

能。本地监测、声光报警、语音求助都在板端 homemon 里，断网照常；告警与安全日志留在板端，网络恢复后云端同步恢复（云端补传队列是后续项，不夸大成已实现）。这是"本地优先"架构最直接的价值。

**5. 多终端协同推送怎么实现？**

状态以设备为准，一路 MQTT 主题多端订阅：板载屏、手机 APP、云端 worker 看到的是同一份状态；监护人账号可在多终端登录查看，告警确认与设备 ACK 双向同步。多角色（网格员/物业）是后端已预留、后续扩展的方向，当前演示聚焦监护人闭环。

### 压力题

**1. 同类队伍很多，差异化在哪？**

三点：**本地优先的应急闭环**（断网可用）、**设备级 ACK 闭环**（HTTP 202 不等于处置完成）、**可扩展多节点协议同构**（加房间零改代码）。很多队伍停在"能演示一次"，我们做到了"连续跑、坏了能自愈、处置有回执"——这是演示型项目和工程型项目的差别。

**2. 现阶段不足和后续方向？**

如实说三条：①视觉是规则+关键点，不是训练分类器，不宣称准确率，后续可接毫米波/更高精度模型；②当前是单家庭、单 ECS 单点，多家庭/高并发需要换数据库与水平扩展；③产品化还差防护外壳、电池与功耗设计。这些都在 `KNOWN-RISKS` 里写清楚了，不藏着。

**3. 老人抵触安装怎么办？**

无摄像头监控感、可随时暂停监护、定位是"安全辅助"不是"监视"；由社区网格员讲清跌倒/燃气应急价值；老人保留自主控制权。隐私设计（不录像、不留存）本身就是降低抵触的关键。

## 三、30 秒开场（可背）

> 我们做的是一套面向独居老人的居家安全系统：感知节点 + OpenHarmony 边缘主控 + 云端 + 监护人 APP。和同类方案最大的不同是**把安全闭环做实了**：本地优先，断网也能报警；视觉只提交受限事件，不污染告警；处置必须设备回 ACK，而不是"消息发出去就算完成"；新增房间不用改代码。这套链路是在真机上跑通、并做过全链路体检的。

## 四、三条红线（答辩别踩）

1. 不说"星闪、无摄像头、电池续航 8–12 个月、IP65、工业级、软著、准确率"——都没有或未验证；
2. 视觉是"关键点 + 时序规则"，不是医疗诊断，不说"预测疾病"；
3. 不把"演示机位调参"说成"验收通过"，实测边界要主动讲。
