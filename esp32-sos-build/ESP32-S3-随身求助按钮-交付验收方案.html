2. 接线方案（物理操作，需你亲手完成）

默认假设（可按实际硬件调整）：按钮为2 脚常开轻触开关；蜂鸣器为3 针低电流有源蜂鸣器模块。所有器件与 ESP32 板必须共地。

GPIO4 按钮输入 GPIO6 蜂鸣器输出 电源 GND 共地

接线明细表

器件器件引脚ESP32-S3 引脚说明
求助按钮（常开）脚 1GPIO4内部上拉已开，悬空=高电平；按下拉低触发
脚 2GND不可接 3V3（按下会直接短路电源）
有源蜂鸣器模块VCC3V3（或按标称 5V0）先查模块标称电压；5V 模块接 3V3 可能不响
I/OGPIO6高电平鸣响（固件默认 GPIO6）
GNDGND共地必需

备选引脚：按钮也可用 GPIO15（bathroom 节点实测内部上拉可靠）或 IO35/36/37（仅输入脚，但 IO35 上拉实测不可靠）。若你的板 GPIO4 已被占用，改 CONFIG_NODE_SOS_GPIO 并同步改接线即可。GPIO6 与摄像头 DVP OV_D2 冲突——本板不插摄像头模组。

5. 验收流程（三阶段，逐级取证）

  1. 阶段 A · 离线按键验收（LOCAL BENCH）
    配 CONFIG_NODE_LOCAL_BENCH=y 跳过 WiFi/网关，烧录后开串口监视。
    预期：未按时打印 SOS raw=0；按下约 200ms 内打印变化与事件。验证：按键电气连接、消抖逻辑、上电防误报。
  2. 阶段 B · 无线接入与求助上报
    正常模式烧录（注入真实 WiFi/网关）。板子连 WiFi → TCP 到 Bridge（PC 上 mqtt_bridge.js）。
    预期：串口出现 WiFi/Gateway 连接日志；按下按钮 → 桥接日志出现 MANUAL_SOS 事件（deviceId=esp32-sos），MQTT 主题收到告警报文。证据：串口日志 + 桥接日志时间戳对齐。
  3. 阶段 C · 告警链路闭环（云 + 本地声光）
    预期：OneNET/后端收到求助事件，监护人端（手机 App/小程序）可见；本地蜂鸣器鸣响、SOS 语音播放；下发 ACK/reset 后静音并重新武装。证据：云控制台记录 + 屏显截图/录像 + 桥接 ack 回环日志。

验收证据清单（每条须留档）

  • 接线照片（按钮、蜂鸣器、共地点特写）
  • 阶段 A 串口日志（按下/松开 raw 电平变化）
  • 阶段 B 桥接日志中 esp32-sos 的 MANUAL_SOS 报文
  • 阶段 C 云控制台事件记录 + 板端告警录像（≤5min 演示素材可裁剪）
  • ACK/reset 回环验证记录（静音 → 再次按下可重新触发）

6. 风险与回滚

风险应对
误刷现有节点板（COM4/COM5 两块在线）只连目标板；chip_id 确认；原工程 bathroom/living 构建产物仍在 D:\OpenHarmony\competition\esp32-node\build-*，可随时回刷原固件
蜂鸣器电流超过 GPIO 驱动能力（>20mA）改用 NPN 三极管（如 S8050）+ 限流电阻驱动；GPIO6 只给控制信号。两线裸蜂鸣器同理
按钮悬空/常闭触点固件 released_seen 机制：上电必须先见"松开"才允许触发；接线后先按一次-松开再按一次验证
网络参数变化（换 WiFi/网关）重跑烧录脚本注入新参数；副本 .local 配置可复用，不写源码
路径过长导致编译异常若 ninja 因路径 >250 字符失败，将副本移到短路径（如 D:\esp32-sos-build）重建
